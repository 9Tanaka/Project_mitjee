## Invariants and interpretation of the decision rule

Code is the source of truth. `calculateResult` dispatches on the pinned immutable template evaluation mode. For `DECISION_RULES_V1`, C means existence of a backend-validated critical event; T means backend completion at the template terminal state; N and U are the existing encountered-checkpoint unassessed and review counts. C has first priority, followed by missing T/N, then U, then passed. Preserve the additional existing `fullStory && encountered === 0` UNASSESSED guard, early-safe-exit filtering, critical opportunity filtering, and terminal consistency checks. This project must not rewrite that implementation from shorthand.

Current categorical scenario results retain `trainingScore: null`. Historical `LEGACY_WEIGHTED_V1` sessions and their scores remain readable and unchanged. Quiz numeric results remain separate. v6 conversation signals are candidates inspected by existing authored backend guards; backend `progressConversation`, event validation, state transition, CAS, and result calculation retain authority. A validated candidate may participate in the existing backend flow; this does not give the LLM authority. No model, speech provider, telemetry callback, or frontend can confirm actions, critical events, or official results.

Preserve owner checks, immutable pinned templates, idempotency fingerprints/receipts, revision/CAS semantics, all-or-nothing aggregate writes, expiration across provider waits, conflict recovery, sanitized persistence, and no raw provider payload logging. A committed turn survives TTS failure and cancellation. Duplicate turns do not repeat STT/AI/TTS work. Instrumentation must not change reads, retries, deadlines, callbacks, public DTOs, or repository ports.

Do not edit domain rules, provider behavior, public contracts, or frontend for this phase.

Final counting decision: use the internal repository decorator once at the composition root and direct-core harnesses, not instrumentation inside Core. This refines the counting options described below. Prevent nested/double wrapping. HTTP response_sent means Response constructed; WS response_sent means final validated message handed to send, with optional send-callback timing separately labeled and never awaited for business completion. Intermediate committed text in a voice exchange is not final response_sent.

Paid-provider cap: two warmups plus ten measured samples for each text/voice cohort, concurrency one, at most 24 successful dialogue turns in this initial pass (document any necessary setup/opening calls separately). Stop early on repeated authentication/quota/rate failures. Deterministic synthetic runs may use 30 or more samples. Do not expand live sample counts automatically.

Use server-only AsyncLocalStorage to carry a request observation context without changing domain/repository interfaces. Generate a random request ID at HTTP ingress; reuse the existing handler request ID where possible. Each WebSocket message gets its own context starting when its payload is received, including per-message reauthentication and bind. Handshake/bind has a separate trace; never make a socket-lifetime trace into a turn metric. Direct service benchmark traces are explicitly labeled `service`, with authentication unavailable rather than zero. HTTP response completion is response construction/hand-off to framework; socket completion is validated final message handed to transport. Neither claims network receipt/playback latency.

Use monotonic elapsed timing. Keep wall-clock UTC timestamp only as metadata. Maintain span start/end independently from event milestones because voice preflight occurs before STT and further app preflight occurs after it. Overlapping/nested spans must not be added as though exclusive. Emit one bounded summary in finalization, including errors, replay, fallback, and cancellation. Finalize once; ignore late provider completions after timeout and prevent interleaved request contamination.

Privacy-safe fields: random `requestId`; `sessionId` and `turnId` are scoped keyed pseudonyms derived from internal IDs, never raw user-supplied IDs. Use process-scoped random HMAC key or configured server-only telemetry key; no key logging. Scope turn pseudonyms by session. Missing IDs remain null. Allowed metadata: transport, allowlisted operation/stage/provider kind, attempt number, boolean duplicate/fallback, closed error category, counts, durations, schema version. Exclude owner/account IDs, email, cookies/tokens, URL/query strings, database URL, SQL/parameters, audio/base64/transcript, user/character text, prompts, provider response/error objects, and stack traces. Bound records and allowlist fields rather than recursively serializing objects.
