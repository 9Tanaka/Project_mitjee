# Supabase/PostgreSQL setup and data-preservation guide

**Status: preparation instructions only.** There is currently no Supabase project, configured PostgreSQL URL, live PostgreSQL verification, approved data transfer, or cutover. No project was provisioned as part of this work. This guide does not authorize creating a project, changing `.env.local`, running migrations, moving data, or switching the live service.

## Scope and current state

The application currently runs as a custom Node HTTP/WebSocket server and uses Prisma at its persistence boundary. A PostgreSQL preparation branch is not a replacement deployment. The original MySQL implementation remains reproducible at the reviewed Phase 1 baseline commit `91e707f376372aed5bdf415dd7bbb32d58583536`; retain that checkpoint with its instrumentation, migrations, tests, and sanitized baseline before any database source transition.

The repository's `.env.local` remains MySQL-configured and must not be edited by this migration preparation. It is suitable only with the matching Phase 1 MySQL source. The PostgreSQL-prepared source requires PostgreSQL-specific runtime configuration before it can be run against a database. Do not start the prepared source with the existing MySQL URL, and do not point it at the live MySQL runtime. Where schema generation, validation, or build tooling requires a URL, use only the project's documented non-connecting PostgreSQL placeholder for config evaluation; it is not a connection, a test, or permission to run the app or migration command.

The current deployment shape is a persistent Node server with WebSocket support. The checked-in `vercel.json` also declares the Next.js framework. Confirm where the actual custom Node/WebSocket server will run before selecting runtime connection settings; a Vercel deployment needs a separate server/WebSocket architecture decision and must not be inferred from the framework declaration.

## Create a project in the user's Supabase account

All of these are actions for the project owner to take in their own Supabase organization. They are intentionally not performed here.

1. Sign in to the owner-controlled [Supabase Dashboard](https://supabase.com/dashboard), choose the correct organization, and create a new project. The owner selects the project name, region, compute/plan, database password, and backup posture. Supabase project creation provisions a PostgreSQL database and related platform services; see the [Supabase platform overview](https://supabase.com/docs/guides/platform) and [available regions](https://supabase.com/docs/guides/platform/regions).
2. Select a region based on the actual production server location, expected users, latency, and data-residency requirements. A region selection is a data-location choice, not by itself evidence of regulatory compliance.
3. Generate a unique database password in a password manager. Keep it in the owner's password manager/secret store. Do not paste it into chat, commit it, or insert it into a code example. Password characters reserved in a connection URL must be percent-encoded; copy the complete connection string from the Dashboard rather than composing a host, port, or username from memory.
4. Under **Connect** in the Dashboard, copy the connection string for the chosen mode. The pooler host and shared-pooler username are project-specific; do not guess them. Download the project CA certificate from **Database settings** for verified remote connections. For runtime `DATABASE_URL`, retain the host, port, username, password, and database from the connection identity but omit any query string or fragment; configure TLS with the CA variable. For remote migration `DIRECT_URL`, add the pinned Prisma CLI's strict TLS parameters described below.
5. Decide whether the project needs Supabase's Data API. This application uses its own cookie/session authentication and the Prisma-backed Node server; it does not need a browser-to-database connection for the current architecture. If no other feature uses REST/GraphQL or Supabase client libraries, disable the Data API. If it is enabled for a future feature, protect every exposed table/view/function with explicit grants and RLS policies and test both allowed and denied operations. See [Securing your API](https://supabase.com/docs/guides/api/securing-your-api) and [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

Supabase's current guidance selects a connection mode based on where the application runs: direct for a persistent backend on IPv6 (or where IPv4 direct access is available), and the shared **session** pooler as an alternative for an IPv4-only persistent backend. Both direct and session modes preserve session features. The **transaction** pooler is aimed at short-lived/serverless traffic and has prepared-statement/session-state limitations. Because this service uses a persistent Node process, WebSockets, Prisma PostgreSQL adapter pooling, and interactive transactions, use direct first when the actual network supports it; otherwise evaluate session mode. Do not select transaction pooling by default, and never run Prisma migrations through a transaction pooler. Any later transaction-pooler choice requires explicit transaction, prepared-statement, connection, and application tests. Supabase documents connection-mode, IP, and pooler details in [Connect to your database](https://supabase.com/docs/guides/database/connecting-to-postgres).

## Runtime, migration, test, and TLS configuration

Keep these as separate server-side secrets/configuration. Variable names below are names only; angle-bracketed text is a description, not a value to copy into a shell or deploy environment.

| Variable | Use | Required handling |
| --- | --- | --- |
| `DATABASE_URL` | Persistent app's PostgreSQL runtime connection, using the Dashboard-provided direct or session-mode endpoint selected above | PostgreSQL only. Keep on the server. Use the runtime adapter's CA configuration, with hostname verification. Keep the URI to its connection identity; the adapter accepts no query parameters or fragments because TLS is supplied separately. |
| `DATABASE_TLS_CA` or `DATABASE_TLS_CA_PATH` | Runtime trusted Supabase CA, inline PEM or an absolute path to a protected CA file | Keep on the server. Prefer a protected CA file path where supported. Remote TLS must verify the certificate chain and hostname; never use `rejectUnauthorized: false` or plaintext fallback. |
| `DIRECT_URL` | Prisma CLI/migration/admin connection | Use the Dashboard's **direct** connection for migrations. For remote connections, pass the trusted CA file using `sslmode=require&sslaccept=strict&sslcert=<absolute-CA-file-path>`; URL-encode reserved characters in the path. Do not use `sslrootcert` or `verify-full` with the pinned Prisma 7.10 migration engine. Reject transaction-pool URLs and insecure TLS modes. Do not silently fall back to `DATABASE_URL`. |
| `POSTGRES_TEST_DATABASE_URL` | Disposable PostgreSQL integration-test database only | Must name `mitjee_test` or `mitjee_test_<lowercase letters, digits, or underscores>`, must be dedicated to tests, and must have no query parameters or fragment. The guard rejects a test database name matching a PostgreSQL runtime database name even if the hostname or credentials differ. The generic Supabase database name `postgres` is never a test-database exception. |
| `POSTGRES_TEST_TLS_CA` or `POSTGRES_TEST_TLS_CA_PATH` | Optional trusted CA for a remote dedicated PostgreSQL test database | Same certificate and hostname verification requirements as the runtime. Do not relax TLS to make a test connect. |

Prisma ORM v7 reads CLI datasource configuration from `prisma.config.ts`; v7 uses `datasource.url` there (the old schema `directUrl` property is removed). This repository deliberately gives that CLI configuration `DIRECT_URL`, while the running application's `PrismaPg` adapter gets `DATABASE_URL`. The migration guard permits only `sslmode`, `sslaccept`, `sslcert`, optional `schema=public`, and optional `connect_timeout` from 1 to 60 seconds; repeated or other options are rejected. Remote CLI TLS requires `sslmode=require`, `sslaccept=strict`, and a readable CA file at `sslcert`. Keep this split explicit in deployment and local secret managers. See the [Prisma v7 config reference](https://www.prisma.io/docs/orm/v7/reference/prisma-config-reference).

For Supabase's CLI/migration connection, use a direct endpoint and the pinned Prisma 7.10 engine's strict TLS parameters: `sslmode=require`, `sslaccept=strict`, and `sslcert` pointing to the downloaded Supabase CA file. In this CLI path, do not use libpq's `verify-full` or `sslrootcert`; the pinned migration engine does not implement them as expected. `sslaccept=strict` rejects a missing or invalid certificate; never use `accept_invalid_certs`. The prepared runtime adapter uses a different driver: it loads the CA via `DATABASE_TLS_CA` or `DATABASE_TLS_CA_PATH` and configures `pg` with `rejectUnauthorized: true`; it rejects every URL query/hash option so URL parsing cannot override the explicit TLS object. `node-postgres` documents that `sslmode`, `sslrootcert`, `sslcert`, or `sslkey` options in a connection string can replace an explicitly supplied SSL object. The pool is capped at 8 clients with 10-second connection and idle timeouts. See Supabase's [SSL guidance](https://supabase.com/docs/guides/platform/ssl-enforcement) and the [`node-postgres` SSL guidance](https://node-postgres.com/features/ssl).

Do not put any of these values in a `NEXT_PUBLIC_*` variable, client bundle, fixture, committed file, telemetry, or support message. Use the deployment platform's server-only secret store. No password, host, project reference, region, certificate contents, or full URL belongs in this guide. The project's `postgres` role is administrative; create a separate login for the application and separate controlled migration access. Do not share the project owner password with the app.

### Least privilege, Data API, and RLS

This application authenticates users through its existing backend session/cookie path and applies owner checks in its application/domain/repository flow. A direct Prisma connection is not a Supabase Data API request and does not automatically receive the Data API's `anon`/`authenticated` JWT context. Supabase's Data API checks both Postgres grants and RLS policies; a policy does not grant table privileges by itself. Supabase's `service_role` and secret API keys bypass RLS and must remain server-only. Those API keys are distinct from a PostgreSQL connection URL and are not required merely to connect Prisma directly.

Before a real deployment, create a dedicated non-owner runtime login with only the database/schema/table/sequence permissions that the finalized application needs, including any template publication at startup. Derive the exact grants from the final generated schema and integration tests. It must not own application tables or triggers, create/alter schemas, create roles, inherit the admin role, or have `BYPASSRLS`. Inspect effective privileges, including inherited and `PUBLIC` grants. Keep a separate migration/admin credential for schema changes. Do not add the runtime login to `postgres`, `service_role`, `anon`, or `authenticated` for convenience. Supabase recommends per-service roles and limited grants in its [Postgres roles guide](https://supabase.com/docs/guides/database/postgres/roles); also note that the built-in `postgres` role has administrative privileges.

If the Data API is enabled, treat it as a separate public API surface: configure grants and RLS intentionally for every exposed object; test `anon`, authenticated, and denied access; never expose a secret/service-role key. Do not assume Supabase Auth is wired into this application's cookie auth or that RLS replaces existing backend owner checks. If Data API access is not needed, disabling it reduces the exposed surface.

## Runbook A: a new, empty PostgreSQL database

Use only after the owner creates an empty project and separately approves a live connection/migration. This path creates target schema and publishes current immutable templates; it does **not** copy historical MySQL data.

1. Confirm the owner-provided project is the intended **new empty** target. Record its owner, region, endpoint mode, backup/restore plan, and access scope in the private deployment record. Do not point the script at the existing MySQL runtime or an already populated database.
2. Create separate runtime and migration credentials with minimum privileges. Store `DATABASE_URL`, runtime CA, and `DIRECT_URL` in the relevant private environment/secret manager. Keep `.env.local` unchanged. Verify both URLs identify the intended project without echoing them; use the Dashboard's connection details, not guessed hosts/users.
3. Confirm the runtime direct/session connection is PostgreSQL and enforces CA chain plus hostname verification. For remote `DIRECT_URL`, use a direct endpoint with `sslmode=require`, `sslaccept=strict`, and `sslcert` pointing to the trusted CA file. The migration/deploy guard rejects missing `DIRECT_URL`, runtime fallback, non-PostgreSQL scheme, TLS downgrade, transaction-pool endpoint, unreadable CA, unsupported TLS parameters, and unknown URL options.
4. Run `npm run prisma:validate` and `npm run prisma:generate`, then review the schema and generated artifacts. Prepare a separate disposable PostgreSQL test database named `mitjee_test` or `mitjee_test_<lowercase letters, digits, or underscores>`. Point `DIRECT_URL` at that database's direct endpoint and set `POSTGRES_TEST_DATABASE_URL` to the same test database; verify both identities before connecting. Apply the baseline with `npm run db:deploy`, then run `npm run test:postgres` with any required test CA variable. These commands operate on the dedicated test target at this step, never the new Supabase project or live MySQL database.
5. After the dedicated database suite and local source gates pass, obtain explicit authorization before migrating the new empty Supabase target. Set `DIRECT_URL` to the Dashboard-provided direct endpoint for that target, verify its identity without printing the value, then run `npm run db:deploy`. This guard rejects transaction poolers, MySQL, insecure or invalid TLS, and the nonconnecting placeholder, but it does not prove the target is empty. Review the PostgreSQL migration and custom trigger SQL before applying it. Never use this command against a populated database.
6. Only after migrations succeed, start the application and verify direct SQL immutability triggers, schema metadata, app start/resume/message/voice paths, authorization, CAS/receipt behavior, and rollback fault handling. Do not call a mock or placeholder test a PostgreSQL pass. Run `npm run typecheck`, `npm test`, `npm run build`, and `npm run audit:client` as the source verification gates; exact status categories and skipped DB suites are recorded in [the PostgreSQL verification checklist](./postgres-verification.md).
7. Verify the selected Supabase backup mechanism, retention, access, and a restore/recovery rehearsal appropriate to the chosen plan before any production decision. Supabase backup availability and retention vary by plan/configuration; the owner must confirm the actual Dashboard setting. The [backup guide](https://supabase.com/docs/guides/platform/backups) describes the available backup/PITR paths and downtime considerations.

## Runbook B: preserving existing MySQL data

This path is **not currently authorized or implemented**. It requires a separate owner-approved migration/cutover plan and a tested ETL; it is not accomplished by changing Prisma's datasource or replaying the MySQL SQL against PostgreSQL.

1. **Plan and inventory.** Confirm the dataset, source/target owners, application downtime window, target capacity, restore objective, encryption/storage access, and an accountable operator. Inventory all tables/rows, constraints, indexes, triggers, JSON null cases, identifier values, collation-sensitive strings, and time ranges. Rehearse first on isolated restored copies.
2. **Backup and restore rehearsal.** Take a source-consistent MySQL backup and verify it can be restored to an isolated MySQL test instance before using it. The appropriate MySQL backup strategy depends on storage engines and online-write/DDL behavior; for example, MySQL documents that `mysqldump --single-transaction` provides a consistent online snapshot for InnoDB, but that does not replace engine/DDL and backup-integrity checks. See the [MySQL backup methods](https://dev.mysql.com/doc/refman/8.4/en/backup-methods.html). Protect the backup as production data.
3. **Quiesce writes.** Stop or drain every application worker, WebSocket/API process, scheduled job, and operator writer against MySQL; verify no writes continue. Export the final consistent snapshot only after this gate. Keep the original MySQL database and backup unchanged.
4. **Export and transform.** Export logical rows from MySQL and use an explicit, versioned transformation/import process into a fresh PostgreSQL target created by PostgreSQL migrations. Do not replay MySQL DDL or mark MySQL migration history as applied in PostgreSQL. Preserve parent/child order, primary/unique key column order, nullable composite relations, and each RESTRICT/CASCADE action. Keep the intentional absence of an account-owner FK. Never silently trim IDs, lowercase or normalize stored values, or convert string IDs to PostgreSQL UUIDs.
5. **Timestamps.** All inventoried MySQL date-time columns use `DATETIME(3)` and do not carry a timezone. Existing application boundaries treat their epoch-millisecond values as UTC; the migration must interpret historical naive values explicitly as UTC, never as the workstation's local zone. Target `timestamptz(3)` instants and test every default and conversion for exact millisecond round-trip. PostgreSQL stores timezone-aware timestamps internally in UTC and applies the session timezone when displaying them; `timestamp without time zone` silently ignores a zone indicator. See [PostgreSQL date/time types](https://www.postgresql.org/docs/current/datatype-datetime.html).
6. **JSON and nulls.** Map the inventoried JSON columns to the approved PostgreSQL JSONB representation while preserving the difference between SQL `NULL` and JSON `null` (`Prisma.DbNull` vs JSON-null behavior). Verify nullable nested JSON, arrays, snapshots, and canonical comparison independent of object-key order. JSONB normalizes key order and drops duplicate object keys; PostgreSQL also rejects some invalid Unicode escapes, so validate data before import rather than assuming every MySQL JSON payload is byte-identical. See [PostgreSQL JSON types](https://www.postgresql.org/docs/17/datatype-json.html).
7. **Collation gate.** The source uses binary `utf8mb4_0900_bin` for primary training/account data and `utf8mb4_unicode_ci` for quiz data. A deterministic PostgreSQL `C` collation is suitable only for the approved binary-like comparison cases; it is not equivalent to arbitrary MySQL case/accent/padding rules. Before migration, audit identifiers and unique values for case variants, accents/Unicode normalization, trailing spaces, ordering, and uniqueness—including quiz IDs, owner IDs, request IDs, mode/version/blueprint. Run equivalence tests against the actual MySQL source. If noncanonical values or collisions exist, stop and obtain an explicit ASTRA collation/index decision. Do not silently rewrite data. PostgreSQL's deterministic/nondeterministic collation semantics are described in [Collation Support](https://www.postgresql.org/docs/current/collation.html).
8. **Load and verify.** Import rows into the isolated, migrated target in dependency order. Compare per-table counts, primary/unique keys, foreign-key integrity, canonical aggregate hashes, JSON semantics, UTC milliseconds, fixed-`CHAR` round trips, and every historical legacy weighted and categorical result. Exercise account normalized-email concurrency, quiz receipts, ownership, result-once, template immutability, one-winner CAS, and rollback behavior. Document all discrepancies and resolve them before any cutover request. PostgreSQL's `pg_dump`/`pg_restore` utilities support PostgreSQL logical backups; they do not transform a MySQL source into PostgreSQL. See [`pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html).
9. **Cutover gate.** Only after ASTRA review, successful disposable-database verification, owner approval, and a tested rollback/reconciliation runbook may a separate change request schedule production cutover. No dual writes are introduced by this preparation.

### Custom invariants that the PostgreSQL migration must preserve

The baseline PostgreSQL migration must include schema-qualified trigger functions/triggers for the three existing MySQL protections:

- `ScenarioTemplateVersion` **BEFORE UPDATE** and **BEFORE DELETE** always raise `PUBLISHED_TEMPLATE_IMMUTABLE` with a PostgreSQL-supported exception SQLSTATE such as `P0001`. Even a no-op update must be rejected.
- `UserAccount` **BEFORE UPDATE** raises `ACCOUNT_ID_IMMUTABLE` if `NEW.id IS DISTINCT FROM OLD.id`; same-ID updates return `NEW` and are allowed.

Keep trigger ownership/control restricted to migration/admin access; the application runtime role must not alter or disable the triggers. Preserve all inventoried PK/unique/index/FK definitions and actions. No SQL `CHECK` constraints existed in the MySQL migration history, so do not invent business constraints in this migration.

## Rollback and data authority

Before cutover and before PostgreSQL accepts production writes, return to the preserved Phase 1 MySQL source commit `91e707f376372aed5bdf415dd7bbb32d58583536` and its existing MySQL database/configuration. Do not alter `.env.local` to test the new source; use separate process/deployment secrets. Keep old MySQL available until PostgreSQL checks pass and the owner approves a cutover.

After PostgreSQL accepts any production writes, **do not blindly point the application back at MySQL**. That can discard newly committed data. Stop writes, preserve both sides, determine the authoritative timeline, and make an explicit reconciliation or forward-fix decision with the owner. No automatic reverse migration, destructive rollback SQL, or dual-write path is provided.
